# OGBデータ研究所｜全体設計・開発マスタープラン

更新日：2026-11-17
対象：ogb-umalab.com のデータ研究所領域。競馬データの日次更新・ニュース配信は本計画の変更対象外。

## 0. 最優先原則

- **全体像 → 対象利用者の検証 → 業務フロー設計 → 基本機能の横断的完成 → 詳細改善** の順で進める。
- 目についた小さな不具合は原則バックログへ記録。データ消失・誤計算・セキュリティ問題のみ優先して割り込む。
- コミット数やツール数を成果指標にしない。利用者が完了できる業務と、その検証結果を成果指標にする。
- AdSense審査対策とツールの事業価値は別の評価軸として管理し、審査結果を保証しない。
- 各作業の開始前に「今回の目的・計画上の位置・完了条件」を確認し、終了時に進捗と残課題を更新する。

## 2. サイトの完成形（仮説）

「データの整理・照合・分析・判断」を、専門知識や高価なソフトがなくても一連の作業として実行できる研究・実用サイト。

利用者が迷わず「自分の課題を選ぶ → 入力データを確認する → ツールを使う → 結果を理解する → 次の判断をする」まで進めることを目指す。

### 構成案

1. **課題別入口**：誰が、何に困っているかから選択
2. **業務フロー別ツール**：複数ツールを一連の作業に接続
3. **検証可能な解説・事例**：サンプル入力、計算根拠、出力例、解釈、限界
4. **研究・開発記録**：開発目的、検証方法、改善履歴
5. **信頼情報**：運営方針、データ取扱い、問い合わせ等の整備状況を確認

## 3. 専門分野の選定（未決定）

| 候補 | 想定する課題 | 既存資産との接続 | 未検証事項 |
|---|---|---|---|
| 小規模ネットショップ・物販 | 受注集計、入金照合、商品別採算 | 高い | 実際のCSV形式、利用頻度、競合との差 |
| 小規模店舗・サービス業 | 日次売上、経費、採算、価格設定 | 中程度 | POS形式、業種差、必要機能 |
| 個人事業主の事務作業 | 請求書PDF整理、名簿・CSV整形 | 高い | 支払意思、既存ツールとの差別化 |
| 小規模チームのデータ業務 | 複数CSV統合、品質検査、レポート | 高い | 課題の具体性、導入の難しさ |

**現段階では特定分野に決定しない。** 需要、競合、解決できる作業時間、技術難易度、既存資産、独自の検証事例を同じ尺度で比較して決める。

## 5. 評価指標（異なる目的を混同しない）

- **業務価値**：代表業務を完了できる割合、必要な手順、入力データへの適合
- **品質**：誤計算・データ欠落の検出、ブラウザ回帰テストの実行結果
- **発見可能性**：検索表示、流入、課題別ページへの到達
- **利用実態**：ツール利用・再訪・途中離脱（計測できる範囲で）
- **AdSense**：ポリシー適合状況、審査結果と指摘事項。インデックス数だけで承認を判断しない

## 6. 直近の作業順序

1. リポジトリ内のページ・ツール・ガイド・テストの全件一覧を確定する。
2. 各ツールの「対象者／入力／出力／完了する業務／未検証事項」を1行ずつ記録する。
3. 専門分野候補の競合・需要を調査し、評価表で比較する。
4. 対象を決めた後、サイト全体の情報設計と3本程度の代表業務フローを先に完成させる。
5. フローの欠けた部分だけ実装し、その後に細かな改善へ進む。

## 7. バックログと作業停止ルール

- **優先度A（即対応）**：誤計算、データ欠落、機密情報露出、主要フローの停止
- **優先度B（計画内で対応）**：代表フローに必要な未実装機能、入力形式の不一致
- **優先度C（記録して保留）**：軽微な文言修正、細かなUI調整、既存の動作に影響しない追加案
- 各変更後は変更ファイルを再取得して確認する。静的検査と実ブラウザ検査は結果を区別して記録する。
- 毎回の作業報告には「フェーズ／完了した成果／未検証事項／次の優先作業」を記載する。
